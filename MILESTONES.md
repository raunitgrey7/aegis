# Aegis — Build Plan & Milestones

This file is the execution contract for the build. Every milestone has a definition of done
and is checked off only when the code runs and the tests pass.

## Principles (non-negotiable)

1. **AI is not the detector.** Detection is deterministic (rules), statistical (baselines), and behavioral (sequences).
   The LLM only plans, summarises, and explains — and every sentence it produces must cite evidence IDs that exist.
2. **₹0 API-key dependency.** Local LLM via Ollama; local embeddings; public threat-intel feeds cached locally.
   The platform must degrade gracefully (deterministic synthesizer) when no LLM is available.
3. **Telemetry is hostile.** Every log line is attacker-controlled text. Prompt-injection defence is an architectural
   property, not a prompt trick.
4. **Reproducible.** The simulator + benchmark produce the numbers in the README. No hand-typed metrics.

| M0 | Repo skeleton, tooling, this plan | venv, Next.js scaffold, CI config, LICENSE | ✅ |

| M2 | Detection engine | YAML rule DSL (match / threshold / sequence), statistical baselines (login-hour, first-seen IP, bytes-out MAD z-score, process rarity), behavioural chains | ✅ |
| M3 | Threat-intelligence engine | Local IOC store (IP/domain/hash/URL), feed loaders for public formats (Feodo, URLhaus, abuse.ch), IOC extraction + matching, risk contribution | ✅ |
| M4 | Correlation engine + attack graph | Entity/time-window clustering of detections into incidents; kill-chain phase ordering; security knowledge graph (networkx); layered attack-graph layout for the UI | ✅ |
| M5 | MITRE ATT&CK mapping + risk scoring | Technique catalogue, tactic coverage, weighted risk score 0–100 with explanation, confidence | ✅ |
| M6 | AI investigation engine | Planner → Identity / Process / Network agents → Evidence agent → Reconstruction → Synthesizer (Ollama or deterministic); evidence-grounding validator; prompt-injection guard | ✅ |
| M7 | Secure API layer | FastAPI, JWT + RBAC, API keys for ingest, rate limiting, audit log, input size limits, tenant isolation, Prometheus metrics | ✅ |
| M8 | Enterprise simulator | Synthetic org (users/hosts/servers/network), benign telemetry generator, 8 attack scenarios (A–H) with ground truth | ✅ |
| M9 | Evaluation harness | 100 attack + 100 benign scenarios → detection rate, FPR, chain reconstruction, technique classification, evidence coverage, latency. Results committed as JSON + Markdown | ✅ |
| M10 | Web UI | Overview, Incident Explorer, Attack Graph, Threat Map, Investigation Copilot (Next.js + Tailwind + React Flow + Recharts) | ✅ |
| M11 | Docs | Architecture, threat model, detection rules reference, API reference, evaluation methodology, runbook | ✅ |
| M12 | Deployment | Docker Compose (Postgres, Redis, Ollama, API, worker, web, Prometheus, Grafana), Makefile, GitHub Actions CI | ✅ |
| M13 | Pitch deck | `pitch/Aegis-Pitch-Deck.pptx` generated by `pitch/build_deck.py` from real benchmark output — charts, tables, trees | ✅ |
| M14 | Public GitHub repository | Pushed, CI green, README with screenshots/diagrams | ✅ |

## Sequencing rationale

Schema (M1) first because every other component depends on it. Detection (M2) before the simulator (M8) so the
simulator is written against the rule DSL rather than the other way round. Evaluation (M9) before the UI (M10)
because the UI shows benchmark numbers. Deck (M13) last because it consumes real results.
